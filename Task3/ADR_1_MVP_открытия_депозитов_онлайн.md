### <a name="_qmphm5d6rvi3"></a>**Решение**

- [Диаграмма контекста  в модели C4](./C4_Context_Diagram.puml)
- [Диаграмма контейнеров в модели C4](./C4_Container_Diagram.puml)

**Детализируем контейнеры системы MVP открытия депозитов онлайн, учитывая нефункциональные требования:**

a. **Требование +R1, +R2.** Для обеспечения безопасности и шифрования трафика выбираем HTTPS для всех внешних взаимодействий. Сайт и интернет-банк будут использовать существующую инфраструктуру SSL-сертификатов банка.

b. **Требование +R3.** Для избежания прямой работы интернет-банка с API АБС создаем промежуточный сервис Application Service, который будет буферизировать заявки и передавать их в АБС пакетно. Это решение также решает проблему перегруженности базы данных АБС (+R4).

c. **Требование +R5.** Учитывая несовместимость текущей версии интернет-банка с Kafka, используем MSMQ/RabbitMQ для очереди заявок. Это обеспечивает надежную доставку сообщений без изменения существующей архитектуры интернет-банка.

d. **Требование R1, R2, R3.** Для обеспечения работы сервисов 24/7 и доступности 99,9% выбираем Java Spring Boot для новых сервисов, так как у команды есть опыт работы с этой технологией, что обеспечивает качество и скорость разработки.

e. **Требование P1, P2.** Для обеспечения быстрого отклика по операциям в миллисекундах создаем отдельный Rate Service с собственной PostgreSQL базой данных. Это решает проблему медленной загрузки справочных данных и обеспечивает единую точку хранения ставок.

f. **Требование R4, R5.** Для обеспечения равномерного горизонтального масштабирования и распределения запросов между серверами используем микросервисную архитектуру с отдельными контейнерами для каждого сервиса. Это позволяет независимо масштабировать компоненты системы.

g. **Требование +R6, +R7.** Учитывая ограничение работы в одном ЦОД на одной группе серверов, но наличие резервного ЦОД для переключения, проектируем сервисы с учетом возможности репликации данных между ЦОД.

h. **В качестве баз данных для новых сервисов используем PostgreSQL как допущение.** Так как дополнительных требований на этот счет нет, можно выбрать СУБД в рамках отдельного ADR под каждую функцию или сформировать дополнительные нефункциональные требования.

**Детализируем интеграции с существующими системами, учитывая архитектурные ограничения:**

a. **Требование +R4.** Так как АБС не может обеспечить требуемое время отклика из-за перегруженности базы данных, выносим функционал работы со ставками в отдельный Rate Service с собственной базой данных. Это снижает нагрузку на АБС и обеспечивает быстрый отклик для клиентов.

b. **Требование +R3.** Для предотвращения прямой интеграции интернет-банка с АБС используем буферизированный подход через Application Service и очередь сообщений. АБС будет обрабатывать заявки пакетно, что выравнивает нагрузку и не требует изменения архитектуры АБС.

c. **Возможно, задача по модернизации АБС потребует отдельного архитектурного решения с определением требований.** Мы делаем допущение, что проблема с нагрузкой решается через вынос функционала в отдельные сервисы. При развитии функционала можно будет перейти на более подходящие решения.


### <a name="_bjrr7veeh80c"></a>**Альтернативы**

**Альтернатива 1: Использование ASP.NET MVC вместо Java Spring Boot**

*Описание:* Разработка новых сервисов (Rate Service, Application Service) на платформе .NET с использованием ASP.NET MVC, что обеспечит единообразие с существующим интернет-банком.

*Преимущества:*
- Единая технологическая платформа с интернет-банком
- Возможность переиспользования существующих компонентов
- Знания команды в области .NET
- Интеграция с существующей инфраструктурой Windows

*Недостатки:*
- Ограниченная экосистема для микросервисов по сравнению с Java
- Привязка к платформе Microsoft
- Потенциальные проблемы с производительностью при высокой нагрузке
- Сложность горизонтального масштабирования

**Альтернатива 2: Использование Oracle вместо PostgreSQL**

*Описание:* Использование Oracle Database для новых сервисов для обеспечения совместимости с существующей АБС.

*Преимущества:*
- Единая СУБД с АБС, упрощение администрирования
- Возможность прямых SQL-запросов между системами
- Использование существующих лицензий Oracle
- Знания команды в области Oracle

*Недостатки:*
- Высокая стоимость лицензий Oracle
- Перегруженность основной БД АБС (требование +R4)
- Сложность масштабирования Oracle
- Привязка к коммерческой СУБД

**Альтернатива 3: Добавление API Gateway для разгрузки**

*Описание:* Внедрение API Gateway (например, Kong, AWS API Gateway, или собственное решение) для централизованного управления API, кэширования, rate limiting и балансировки нагрузки.

*Преимущества:*
- Централизованное управление API
- Встроенное кэширование и rate limiting
- Упрощение мониторинга и логирования
- Возможность A/B тестирования
- Дополнительный уровень безопасности

*Недостатки:*
- Дополнительная точка отказа
- Усложнение архитектуры
- Необходимость обучения команды
- Дополнительные затраты на инфраструктуру

### <a name="_недостатки_ограничения_риски"></a>**Недостатки, ограничения, риски**

**Недостатки выбранного решения:**

1. **Сложность архитектуры:** Введение дополнительных сервисов увеличивает сложность системы и количество точек отказа.

2. **Необходимость синхронизации данных:** Rate Service и АБС должны синхронизировать данные о ставках, что может привести к рассинхронизации.

3. **Дополнительные затраты на инфраструктуру:** Новые сервисы требуют дополнительных серверов, мониторинга и поддержки.

4. **Зависимость от очереди сообщений:** Application Queue становится критическим компонентом, отказ которого блокирует обработку заявок.

**Ограничения:**

1. **Технологические ограничения:** Использование MSMQ/RabbitMQ вместо Kafka может ограничить возможности масштабирования в будущем.

2. **Ограничения PostgreSQL:** При росте нагрузки может потребоваться переход на более производительную СУБД.

3. **Ограничения Java Spring Boot:** При очень высокой нагрузке может потребоваться переход на более производительные технологии.

**Риски:**

1. **Риск рассинхронизации данных:** Между Rate Service и АБС могут возникнуть расхождения в ставках.

2. **Риск отказа очереди:** При отказе Application Queue заявки не будут обрабатываться.

3. **Риск перегрузки новых сервисов:** При неправильном масштабировании новые сервисы могут стать узким местом.

4. **Риск сложности поддержки:** Увеличение количества компонентов усложняет диагностику проблем.

5. **Риск vendor lock-in:** Привязка к конкретным технологиям может ограничить возможности миграции в будущем.
